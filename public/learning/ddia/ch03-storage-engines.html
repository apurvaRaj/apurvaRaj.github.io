LSM-tree

Write fast now, tidy up later

Write path

Each write is appended to the WAL on disk, in arrival order, and inserted into the memtable in memory, which is kept sorted. Nothing is written to an SSTable at this point.

When the memtable fills up (not the WAL), it is written to disk as a new SSTable: an immutable, sorted file. The WAL for that memtable is then deleted, because the data is safe on disk.

Read path

Check the memtable, then SSTables from newest to oldest. Bloom filters let the engine skip files. Stop at the first match, because the newest version wins.

Compaction

In the background, merge some SSTables (not always all) like a merge sort. Keep the newest value per key, drop overwritten values and tombstones, write new files, delete the old ones.

Why a memtable if the WAL holds the same data?

Same data, different shape. The WAL is unsorted, in arrival order: good for crash recovery, useless for lookups. The memtable is sorted (a skip list or balanced tree), so recent reads are fast and the flush writes a sorted file in one pass. The WAL is read only after a crash, to rebuild the memtable.

SSTable properties

Sorted by key, each key at most once per file, immutable. Split into compressed blocks, with a sparse index (first key of each block) and a Bloom filter. It is never sorted on disk: it is born sorted, because the memtable is sorted at flush and compaction merges already-sorted files.

Order is byte order, so "10" sorts before "9". Use fixed-width or zero-padded keys, such as TCS#2026-11-20.

Chunking and sizes

Writes are not chunked up front. Each write goes into the memtable one at a time. File boundaries come later: a flush turns one full memtable into one file, and compaction cuts its output into files of a target size. All sizes are tunable. RocksDB, for example, defaults to about a 64 MB memtable, about 64 MB target files and 4 KB blocks. A bigger memtable means fewer flushes, more memory, and a slower WAL replay after a crash.

Why is it called a tree?

From the 1996 paper by O'Neil and colleagues, where the structure was a series of trees, one in memory and several on disk, merged downwards. Modern engines are a sorted memtable plus levels of sorted files: a layered hierarchy, not a tree you search by following pointers.

        Bloom filter

        A card of ticked boxes that says "no" or "maybe"

        The problem it solves

        A read checks SSTables one by one, and each file read is slow. For a key that doesn't exist, the engine would open every file just to prove it isn't there. A full list of keys per file would use too much memory. A Bloom filter is a small row of bits per file, kept in memory, that answers "could this key be here?"

        How it works

        Picture a card with 16 numbered boxes in front of a shelf. When a key is added, fixed rules (hash functions) turn it into box numbers, and those boxes are ticked. To check a key, apply the same rules:

        • Any box empty → the key was never added → definitely not here. Skip the file.
        • All boxes ticked → maybe. Read the file. Other keys may have ticked those boxes, which is a false positive.

        Boxes are never unticked, so a key that really is there always finds its boxes ticked. There is never a false "no".

        One filter per SSTable, sized to it

        Each SSTable gets its own filter, built when the file is written. Its size is the file's key count times a bits-per-key setting, so files differ in size but share a false-positive rate. About 10 bits per key gives about 1% false positives. It is stored inside the SSTable and loaded into memory when the file is opened. It can't grow or delete keys, which is fine because SSTables never change. Compaction builds a new filter for each new file.

        B-tree

        One home per key, edited in place

        Pages

        Data lives in fixed-size pages (about 4–16 KB). Leaf pages at the bottom hold the keys and values. Inner pages hold keys as signposts plus pointers to child pages. A page with n keys has n + 1 pointers, one per gap.

        Where does a key belong?

        On every page: compare left to right, letter by letter, and stop at the first key bigger than yours. Take the pointer just before it. If none is bigger, take the last pointer. If one is equal, you found it. Real pages use binary search, with the same result.

        root [ITC, TCS]
 BHEL  < ITC                → gap 0 (left)
 SBIN  > ITC, < TCS        → gap 1 (middle)
 WIPRO > ITC, > TCS        → gap 2 (right)
 INFY vs ITC: I = I, then N < T → INFY is smaller

        It always works because every signpost separates its children: everything left of it is smaller, everything right is bigger or equal. A split keeps this true.

        Fetch

        Read the root, pick the gap, read that child, repeat to a leaf. The key is on that leaf or doesn't exist. Cost: one page read per level, the same for a hit or a miss. Real pages hold hundreds of keys, so 3–4 levels cover billions of rows, and the top levels stay in memory.

        Insert

        1. Find the leaf, as in a fetch.
        2. Write the change to the WAL first.
        3. If the leaf has room: put the key in sorted position, rewrite the page in place. 1 page written.
        4. If it's full: split it. The left half stays, the right half goes to a new page, and the middle key moves up to the parent.
        5. If the parent overflows, it splits too. If the root splits, a new root appears, and the tree grows one level taller at the top. That keeps every leaf at the same depth.

        B+-trees

        InnoDB and PostgreSQL use B+-trees: inner pages hold only copies of keys as signposts, all values stay in leaves, and leaves link left to right for range scans. The toys here move the middle key itself up, so a fetch can end on an inner page.

            WAL in a B-tree

            Log the change before touching the page

            Why a B-tree needs it

            1. One change can touch several pages. Inserting G changed #1, #5 and #3. A crash after #1 and #5 but before #3 leaves no pointer to #5: INFY is lost and the tree is corrupt.
            2. A page can be half-written. A 16 KB page is bigger than what the disk writes atomically, so a crash can leave a torn page.
            3. Pages change in memory first. The buffer pool holds dirty pages and writes them back later. Recent committed changes may exist only in memory.

            Write path

            1. Change the pages in the buffer pool and mark them dirty.
            2. Append log records, each with an increasing LSN (log sequence number). Each page stores the LSN of its last change.
            3. At commit, flush the log to disk (fsync). Only then reply "committed". Many commits can share one flush (group commit).
            4. Dirty pages are written to disk later by a background process.
            LSN 101  page #1: remove HDFC, INFY; insert G
LSN 102  page #5: new page [INFY]
LSN 103  page #3: insert HDFC + pointer to #5
LSN 104  COMMIT

            Write-ahead rule: a dirty page may reach disk only after the log records for its changes are on disk. The log always runs ahead of the pages.

            When is the log cleared?

            Not at commit. A record can be freed only when its page change has reached disk. The checkpoint marks how far that is true, and it can't pass the oldest dirty page. The log is freed from the front, in order.

            LSN 101  page #1 → flushed
LSN 102  page #5 → still dirty   ← checkpoint stops here
LSN 103  page #3 → flushed
LSN 104  COMMIT
Freeable: up to 101. After #5 is flushed, the checkpoint moves on.
            • InnoDB: a fixed-size redo log used in a circle; space behind the checkpoint is overwritten. If it nearly fills, dirty pages are forced out and writes stall.
            • PostgreSQL: 16 MB WAL segments, recycled or deleted after a checkpoint, unless a replica's replication slot, archiving or wal_keep_size still needs them. A dead replica with a slot can fill the disk.

            More frequent checkpoints mean faster recovery but more page writing.

            Crash recovery

            1. Find the last checkpoint.
            2. Redo: replay records forward; apply a record if its LSN is newer than the page's LSN.
            3. Undo: roll back transactions that never committed (InnoDB uses undo logs; the method is known as ARIES).

            Torn pages: InnoDB's doublewrite buffer writes each page to a side area first; PostgreSQL logs the full page on its first change after a checkpoint.

            Other uses: replication (PostgreSQL streams WAL; MySQL uses the separate binlog), point-in-time recovery, and change data capture (e.g. Debezium).

            Interview lines: say each in about 30 seconds

            LSM-treeAn LSM-tree turns writes into sequential I/O. Each write is appended to a WAL and inserted into a sorted in-memory memtable. When the memtable is full, it's flushed as an immutable sorted SSTable and that WAL is dropped. Reads check the memtable, then SSTables newest to oldest, with Bloom filters to skip files. Background compaction merges files, keeps the latest value per key and removes tombstones.
            Bloom filterEach SSTable has its own Bloom filter, built when the file is written and sized by its key count times a bits-per-key setting. It answers "definitely not here" or "maybe", never a false no, so reads can skip files safely. About 10 bits per key gives about 1% false positives.
            B-treeA B-tree stores keys in fixed-size pages arranged as a balanced tree. A read walks root to leaf, one page per level, so the cost is predictable. A write overwrites the leaf page in place; a full page splits and pushes its middle key up, and a root split adds a level at the top.
            WAL in a B-treeA B-tree overwrites pages in place, and one insert can touch several pages, so a crash could corrupt the tree. The WAL logs each change sequentially and is flushed at commit, before the pages are written. Dirty pages are flushed lazily, and after a crash the database redoes the log from the last checkpoint and undoes uncommitted transactions.
            When is the log cleared?Not at commit. It's freed after a checkpoint, once the oldest dirty page has been written to disk. InnoDB reuses a fixed-size circular redo log. PostgreSQL recycles WAL segments unless replicas or archiving still need them.
            Why "tree"?The name comes from the 1996 paper, where the structure was a series of trees merged downwards. Modern LSM engines are a sorted memtable plus levels of sorted files: a hierarchy, not a tree you search by pointers like a B-tree.

            Memory hooks

            Log, Sort, MergeLSM in three words. Log the write, sort it in memory, merge files on disk later.
            The memtable fills, not the WALThe memtable's size triggers the flush. The WAL is just a receipt roll kept for crashes.
            Born sortedSSTables are never sorted on disk. The memtable is sorted at flush; compaction merges sorted files.
            Bloom says no or maybeNever a false "no". Sometimes a false "maybe". That's why it can safely skip files.
            First key bigger than yoursThe routing rule on every page. Take the pointer just before it.
            Middle goes upA full page splits in two and pushes its middle key to the parent. Trees grow at the top.
            Log runs ahead of pagesThe write-ahead rule. Commit flushes the log; pages follow later.
            Oldest dirty page holds the logThe checkpoint can't pass it, so log space behind it can't be freed.
            Files vs pagesLSM rewrites files (compaction). B-tree rewrites pages (in place). Both are write amplification.
